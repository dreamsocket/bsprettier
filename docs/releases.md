# Releases

The canonical description of *how releases and versions work* for this repo.

This is a monorepo of independently built, tested, versioned, and published
artifacts:

- **CLI / library** — `@dreamsocket/bsprettier`
- **VS Code extension** — `bsprettier-vscode`

## Independent artifact versions

Each package owns its own semantic version in its own `package.json` and may
release on its own cadence (independent patches, hotfixes, etc.). Example: CLI
`1.4.0`, extension `0.8.2`. Extension-only changes bump **only** the extension;
CLI-only changes bump the CLI.

## Artifact relationship (current)

The extension **bundles the CLI at build time** — esbuild inlines
`@dreamsocket/bsprettier` into the VSIX. Consequence: **a CLI change requires a
new extension release** so the bundled copy is updated. This propagation is
automated (the release tooling bumps the extension whenever the CLI it depends on
changes). The reverse does not hold — extension-only changes never bump the CLI.

> Future option: switch the extension to consume the *published* CLI (the
> Prettier/ESLint "use the project's install" model) instead of bundling. That
> makes versioning fully trivial but depends on the CLI being published to npm.

## Git tag conventions

Artifact-scoped tags keep Git history unambiguous about *what* released:

- `cli-vX.Y.Z` — a CLI release
- `vscode-vX.Y.Z` — an extension release

There is **no repo-wide or dated umbrella tag**. Each artifact releases on its
own track; change magnitude lives in each artifact's semver (major = breaking,
minor = feature, patch = fix), driven by conventional commits.

## GitHub Releases = one release per artifact

There is no coordinated "release train" / compatibility bundle. release-please
creates **one GitHub Release per artifact release**, automatically, when its
release PR is merged:

- A `cli-v*` release — body is the CLI changelog (features / fixes / breaking).
- A `vscode-v*` release — body is the extension changelog; the VSIX is attached
  as an asset.

The repo's Releases page shows the two streams interleaved by date, each prefixed
by component, so the per-artifact history (and where the larger changes are)
stays directly readable.

Because the extension bundles the CLI, the **extension release effectively names
the user-facing bundle** — its version already implies which CLI is inside. To
keep a single obvious "current" entry, the extension release is marked GitHub
"Latest"; CLI releases are marked not-latest.

## Release triggers

CI runs for every pull request, every push to `main`, and manual
`workflow_dispatch` runs. Pull requests are validation only; they do not create
tags, GitHub Releases, VSIX assets, or Open VSX publishes.

release-please also runs on every push to `main` and on manual
`workflow_dispatch` runs. A push to `main` is only the scan trigger. It does not
mean every merge becomes a release. release-please looks at the conventional
commits since the last release for each configured package and opens or updates
artifact-specific release PRs when it finds release-worthy changes.

Commit messages drive semver intent:

- `fix(...)` and other patch-level conventional commit types create patch
  release candidates for the affected artifact.
- `feat(...)` creates a minor release candidate for the affected artifact.
- A breaking-change marker (`!` in the commit header or a `BREAKING CHANGE:`
  footer) creates a major release candidate.
- `docs(...)`, `chore(...)`, `ci(...)`, and other maintenance-only commits do not
  normally create releases unless they carry a breaking-change marker or are part
  of a release PR generated by release-please.

The release itself happens when a release-please PR is merged. That merge updates
the package version and changelog, creates the artifact tag (`cli-vX.Y.Z` or
`vscode-vX.Y.Z`), and creates the GitHub Release. When a `vscode-v*` release is
created, the release workflow also packages the VSIX, attaches it to the GitHub
Release, and publishes it to Open VSX.

The configured release artifacts are `packages/cli` and
`packages/vscode-extension`. Changes should land with a conventional commit scope
that reflects the artifact they affect, for example `fix(cli): ...` or
`feat(vscode): ...`. Because the extension bundles the CLI, release tooling also
bumps the extension when the bundled CLI dependency needs to move forward.

release-please knows which artifact to release from `release-please-config.json`.
The `packages` keys define the release roots:

- `packages/cli` maps to the `cli` component and produces `cli-vX.Y.Z` tags.
- `packages/vscode-extension` maps to the `vscode` component and produces
  `vscode-vX.Y.Z` tags.

The commit scope is useful and should match the artifact, but it is not the only
source of truth. The changed files and configured package roots determine which
package a commit belongs to. A root-only change is not its own release artifact
today; if a root-level packaging or workflow change should force a CLI or
extension release, pair it with the affected package change or update the
release-please config deliberately.

The `node-workspace` plugin handles workspace dependency propagation. The
extension depends on the CLI with `@dreamsocket/bsprettier: file:../cli`, so a
CLI release candidate also causes the extension package to get a matching
dependency bump and extension release candidate. An extension-only change does
not propagate backward into a CLI release.

## Distribution channels

- **CLI**: git install today. Use `npm i -D github:dreamsocket/bsprettier` for
  a project-local install, then run it through npm scripts or one-off with
  `npx --no-install bsprettier`. Use
  `npm i -g github:dreamsocket/bsprettier` for a global terminal command. The
  root package exposes the CLI bin and its `prepare` script builds
  `packages/cli` on install. Publishing to **npmjs.org** is planned but
  deferred.
- **Extension**: the **VSIX** is attached to the `vscode-v*` GitHub Release
  **and** published to **Open VSX** (the registry other VS Code compatible IDEs install from). The
  Microsoft Marketplace is an optional future channel.

## Why a monorepo (not separate repos)

Shared code/types/config, shared CI and tests, easier compatibility validation,
and simpler coordinated releases. We would split into separate repos only if
ownership, release cadence, governance, permissions, or issue tracking diverge
significantly. Current layout: `packages/cli/` (`@dreamsocket/bsprettier`) and
`packages/vscode-extension/` (`bsprettier-vscode`), with an optional
`packages/core/` if shared code is later extracted.
